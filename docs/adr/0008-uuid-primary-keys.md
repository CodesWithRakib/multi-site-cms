# ADR-0008: UUID primary keys, `timestamptz` instants, one `bigint` exception

- Status: Accepted
- Date: 2026-11-01
- Owners: database engineering

## Context

Phase 02 creates eighteen tables at once. Each needs a key strategy, and mixing
strategies table by table is how a schema becomes impossible to reason about. IDs
also appear in admin URLs, audit records, and API payloads, so enumeration and
guessability matter.

Timestamps have the same problem: a single ambiguous local timestamp in a
publishing system produces incorrect scheduling.

## Decision

- **UUID v4** primary keys on every table, defaulted in the database with
  `gen_random_uuid()` (core PostgreSQL since 13, so no extension is required).
- IDs are never generated in application code, so a row has an identity even when
  written by a script or a future worker.
- **Composite unique keys** such as `(id, site_id)` accompany some tables so
  composite foreign keys can prove tenant ownership. They are not alternative
  primary keys.
- **One deliberate exception:** `audit_events.id` is `bigint GENERATED BY DEFAULT
AS IDENTITY`. It is append-only, written in time order, paginated by time, and
  never exposed as a reference target.
- **All instants are `timestamptz` in UTC.** `created_at`/`updated_at` default to
  `now()`; `updated_at` is maintained by the ORM on write.
- Requested versus actual publication time are separate columns
  (`scheduled_for`, `published_at`), never one column with a status flag.

## Alternatives considered

| Option                                   | Why not                                                                    |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `bigserial` everywhere                   | Enumerable IDs in URLs, leaks volume, complicates cross-environment merges |
| UUID v7 (time-ordered)                   | Better index locality, but no first-class generator in core PostgreSQL yet |
| ULID / application-generated IDs         | Two sources of truth for identity; harder for scripts and seeds            |
| `uuid_generate_v4()` via `uuid-ossp`     | Requires an extension for no benefit over core `gen_random_uuid()`         |
| `timestamp` without time zone            | Ambiguous across sites and DST; a publishing platform cannot afford it     |
| MySQL-style auto-increment + public slug | Slugs change; IDs would still enumerate                                    |

## Consequences

Positive: non-guessable identifiers, uniform strategy, no sequence contention,
safe to create rows from any writer, unambiguous scheduling math.

Negative: UUID indexes are larger and less cache-friendly than ordered integers;
random insertion order fragments B-tree pages at high write volume. `audit_events`
keeps its ordered key precisely because it is the highest-volume append table.

Accepted cost: we trade a small index-size penalty for non-enumerability and
consistency. That trade is reconsidered only if a measured write-throughput
problem appears.

## Future migration considerations

If insert locality becomes a measured problem, migrate hot tables to UUID v7 (or
`gen_random_uuid()` plus a time-leading index) in a dedicated migration. The
composite-key relationships would be unaffected. Changing the engine's key type is
otherwise not worth doing.
