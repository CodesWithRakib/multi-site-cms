# ADR-0010: Media as metadata plus opaque storage keys

- Status: Accepted
- Date: 2026-11-01
- Owners: database + backend engineering

## Context

Both publications are image-heavy. Media must be reusable within a site, protected
across sites, deletable only when unused, and portable between a free-tier storage
provider and S3-compatible storage later. Phase 02 must define the data shape now,
without implementing uploads.

## Decision

**PostgreSQL stores metadata only.** Bytes live in object storage.

`media_assets` holds: owning `site_id` (nullable only for Super Admin platform
assets), uploader, `storage_provider`, opaque `storage_key` (unique), `mime_type`,
`byte_size`, `checksum`, optional `width`/`height` (both or neither), `alt_text`,
`caption`, `status`, and a soft-delete timestamp.

Rules:

1. **No binaries in the database.** A bytea column would bloat backups and defeat
   CDN delivery.
2. **No credentials or signed URLs.** A signed URL is a temporary capability, not
   an identifier; storing one would leak access and expire into broken references.
3. **Opaque keys.** `storage_key` is generated by the server; a user filename never
   becomes a key (path traversal, collisions, PII in URLs).
4. **Provider is data, not code.** `storage_provider` plus `storage_key` lets the
   application resolve bytes through an internal interface, so swapping providers
   does not touch content rows.
5. **Usage is explicit.** `post_publication_media` records
   featured/gallery/inline/attachment with a position, plus a featured shortcut on
   the publication. A `RESTRICT` foreign key makes "cannot delete an asset in use"
   a database fact.
6. **Site-scoped by default.** Cross-site reuse requires promoting an asset to
   platform scope, which is an audited Super Admin action.
7. **Deduplication by checksum.** The checksum column and its index make it
   possible to detect duplicates without trusting the client.

## Alternatives considered

| Option                                              | Why not                                                         |
| --------------------------------------------------- | --------------------------------------------------------------- |
| Bytes in `bytea`                                    | Backup size, memory pressure, no CDN, no range requests         |
| One row per site per asset                          | Duplicates metadata and breaks "one asset, one key"             |
| Store the full public URL                           | Pins the provider into content rows and prevents migrations     |
| Signed URL as the identifier                        | Expires; would silently break published articles                |
| JSON gallery arrays on the publication              | No referential integrity, no reverse lookup, no deletion safety |
| A separate `media_usage` row per rendered placement | Premature; ordering plus role covers the requirement            |

## Consequences

Positive: small database, portable provider, safe deletion, per-site isolation,
duplicate detection, and a clear place to validate MIME type, size, and dimensions.

Negative: two systems must stay consistent — a row without bytes is possible until
the upload transaction is defined. Mitigation: create the row only after the object
exists, and mark `status`/`deleted_at` for cleanup rather than deleting rows
immediately.

Accepted cost: soft-delete plus a later cleanup job, rather than instant deletion.

## Future migration considerations

The upload pipeline (presigned URLs, validation, virus scanning, thumbnails) is a
later phase. If multiple providers must be active at once, add a provider registry
in the media module — the schema already carries the provider discriminator. Moving
bytes between providers is a data operation (copy, verify checksum, update
`storage_provider` + `storage_key`) with no schema change required.
