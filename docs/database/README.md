# Database overview

Status: **implemented.** Phase 02 created the schema; no application service
queries it yet. PostgreSQL is the system of record; media bytes live outside it.

## Technology

| Concern        | Choice                                                          |
| -------------- | --------------------------------------------------------------- |
| Database       | PostgreSQL 18 (local: `postgres:18.6-alpine` in Compose)        |
| ORM            | TypeORM, used for entities, migrations, and metadata only       |
| Driver         | `pg`                                                            |
| Schema changes | Explicit, version-controlled migrations; `synchronize` is false |
| Extensions     | `citext`, `pg_trgm`                                             |
| Identifiers    | UUID v4 via `gen_random_uuid()` (built into PostgreSQL 13+)     |
| Timestamps     | `timestamptz`, UTC                                              |

The runtime, the TypeORM CLI, and the integration tests all build their options
through `apps/api/src/database/database-options.ts`, so they cannot drift apart.

## Naming conventions

| Object            | Convention              | Example                            |
| ----------------- | ----------------------- | ---------------------------------- |
| Table             | plural snake_case       | `post_publications`                |
| Column            | snake_case              | `scheduled_for`                    |
| Primary key       | `PK_<table>`            | `PK_post_publications`             |
| Unique constraint | `UQ_<table>_<columns>`  | `UQ_post_publications_site_slug`   |
| Foreign key       | `FK_<table>_<target>`   | `FK_post_publications_revision`    |
| Check constraint  | `CHK_<table>_<rule>`    | `CHK_post_publications_schedule`   |
| Index             | `IDX_<table>_<columns>` | `IDX_post_publications_due`        |
| Partial unique    | `UQ_<table>_<rule>`     | `UQ_site_domains_primary_per_site` |

Every name is written explicitly in the migrations; nothing depends on a naming
strategy at runtime.

## Primary keys

- UUID v4, generated by the database default `gen_random_uuid()`.
- No application-generated IDs, no sequences exposed to clients, no enumerable
  integers on tenant data.
- One deliberate exception: `audit_events.id` is a `bigint` identity column. Rows
  are append-only and read in time order, where an ordered key is cheaper and
  better for pagination than a random UUID. See ADR-0008.
- Composite unique keys such as `(id, site_id)` are not alternative primary keys;
  they exist so composite foreign keys can prove site ownership.

Why UUIDs: publication IDs appear in admin URLs, and sequential integers would
leak volume and invite enumeration. Tenant scoping still has to be enforced by
authorization — a UUID is not a permission.

## Timestamp strategy

- Every instant is `timestamptz` and stored in UTC.
- `created_at` / `updated_at` default to `now()`. `updated_at` is maintained by the
  application on write (no trigger), because a trigger would also fire for
  migrations and audits.
- Requested and actual publication times are separate columns:
  `scheduled_for` (the requested instant) and `published_at` (when it actually
  happened). Scheduling is not a status flag.
- Site-local display time is derived at render time from `sites.timezone`; the
  database never stores an ambiguous local timestamp.

## Migration policy

1. `synchronize: false` in every environment. No exceptions, no `DB_SYNC` flag.
2. Every schema change is a new migration file with an explicit `up` and `down`;
   applied migrations are never edited outside a disposable local database.
3. Migrations are forward-only in production. A defect is fixed by a new forward
   migration; `migration:revert` exists for local development.
4. Migrations are ordered by timestamp and applied once per database; the CLI
   records them in `typeorm_migrations`.
5. Migrations do not seed data. Development seed data is a separate, idempotent
   script that refuses to run when `NODE_ENV=production`.
6. A migration that renames or drops a column ships with the code that has already
   stopped using it (expand/contract), never in the same deploy as the feature.

Commands (run from the repository root):

```bash
pnpm --filter @multi-site-cms/api build
DATABASE_URL=... pnpm --filter @multi-site-cms/api db:migration:run
DATABASE_URL=... pnpm --filter @multi-site-cms/api db:migration:show
DATABASE_URL=... pnpm --filter @multi-site-cms/api db:migration:revert   # local only
DATABASE_URL=... pnpm --filter @multi-site-cms/api db:seed:dev            # after build
```

The CLI runs from `dist/`, so the API must be built first.

## Transaction principles

These operations must run in one transaction once their services exist:

| Operation                           | Why                                              |
| ----------------------------------- | ------------------------------------------------ |
| Changing site domains               | The single-primary invariant can break mid-write |
| Saving a revision with post updates | The post and its revision must agree             |
| Creating/updating a publication     | Publication plus audit event are one fact        |
| Publishing or unpublishing          | State, timestamp, and audit must commit together |
| Changing roles or site access       | A half-applied grant is a security incident      |
| Restoring deleted content           | Restore, publication state, and audit together   |

## Soft-delete policy

Soft delete is deliberately rare:

- `posts.deleted_at` — content deletion is recoverable and audited.
- `media_assets.deleted_at` — blocks new use while storage cleanup is pending.
- Everything else uses explicit lifecycle columns (`status`) or is genuinely
  deleted.

Consequences to honor in services:

- A soft-deleted post must never reach a publication query.
- Slugs of archived or deleted publications stay reserved by the unique
  constraints. That is intentional: a public URL must not silently start serving a
  different article. Reusing a slug requires an explicit redirect decision.

## JSONB policy

JSONB is used only where the shape is owned by something other than the relational
model:

| Column                  | Contents                                      |
| ----------------------- | --------------------------------------------- |
| `post_revisions.body`   | Tiptap editor document                        |
| `sites.settings`        | non-secret branding, SEO defaults, navigation |
| `audit_events.metadata` | action-specific context                       |

Rules: never store authorization facts, relationships, timestamps, or anything
that needs a foreign key in JSON; always add a `jsonb_typeof(...) = 'object'`
check; validate the shape in the application with Zod before writing.

## Indexing principles

- Indexes are created from a named query, not speculatively. Every non-obvious
  index is listed in the data dictionary with the query it serves.
- Tenant-first composite indexes: `(site_id, status, published_at)` for feeds.
- Partial indexes where a status filter dominates: the scheduling worker scans
  only `status = 'scheduled'`.
- Foreign keys are indexed on the referencing side when a reverse lookup is
  expected (`media_id` → "where is this asset used").
- Unique constraints already provide an index; no duplicate BTREE is added for the
  same leading columns.

See [indexing and performance](erd.md#query-patterns) for the query-to-index map.

## Data ownership

Every row is either platform-owned or site-owned; see
[data ownership](data-ownership.md) and
[multi-site isolation](multi-site-data-isolation.md). The short version:

- Global: `users`, `roles`, `permissions`, `role_permissions`, `posts`,
  `post_revisions`, `audit_events` (with a nullable site scope).
- Site-owned: `site_domains`, `categories`, `tags`, `events`, `post_publications`,
  the publication joins, `media_assets` (nullable only for platform assets).

## Super Admin bootstrap

No user is seeded. The first Super Admin must be created by a controlled
procedure, not by an endpoint that anyone can call:

1. An operator supplies `BOOTSTRAP_SUPER_ADMIN_EMAIL` (and, when implemented, a
   one-time token) through the deployment secret store.
2. A CLI task run by the operator creates the user with `status = 'invited'` and
   assigns the `super_admin` role, writing an `audit_events` row with
   `actor_type = 'bootstrap'`.
3. The user sets a password through the reset flow in the authentication phase.

Constraints honored by that design: no default password, no seeded privileged
row, no public promotion path, and a permanent audit record. This procedure is
not implemented in Phase 02; it is specified here and in ADR-0012 so the
authentication phase cannot invent an insecure shortcut.

## Testing

- Unit/contract: `pnpm --filter @multi-site-cms/api test` (no database required).
- PostgreSQL integration: `pnpm --filter @multi-site-cms/api test:integration`
  against `TEST_DATABASE_URL` (default `…/multi_site_cms_test`). The harness drops
  and recreates the `public` schema, then applies every migration, so the chain is
  validated from empty on each run.
- The harness refuses any database whose name does not end in `_test`.
